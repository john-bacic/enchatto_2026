# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Enchatto is a real-time multilingual conversation platform. A host creates a room on iOS; participants join via QR code in the browser. Messages are translated and enhanced in real time by the host device.

## Architecture

- **Monorepo** with npm workspaces: `apps/*` and `packages/*`
- **Web app** (`apps/web/`): Next.js 14 + React 18 participant client. Uses Convex React hooks (`useQuery`/`useMutation`) for real-time subscriptions.
- **iOS app** (`apps/ios/`): SwiftUI host app. Communicates with Convex via HTTP POST actions (polling, not subscriptions).
- **Convex backend**: Schema, queries, mutations, and HTTP actions live in `apps/web/convex/`, the only folder that is deployed. A backup copy exists at `apps/convex/convex/` — keep both in sync, and never deploy from it.
- **Shared types** (`packages/shared-types/`): TypeScript type contracts (Room, Participant, Message, Reaction) used by web and as reference for iOS.

## Commands

From monorepo root (`enchatto/`):

```bash
npm install                     # Install all workspace dependencies
npm run dev:web                 # Start Next.js dev server on :3000
npm run dev:convex              # Start Convex dev watcher
npm run build:web               # Production build of web app
npm run lint                    # ESLint over the web app, Convex functions and tests
npm run typecheck               # tsc over the web app, the Convex functions and the tests (.ts and .tsx)
npm test                        # Convex function tests (vitest + convex-test) and the web's component tests, about 5 seconds, no network
node scripts/check-localization.mjs   # Duplicate keys in apps/ios/Localization.swift crash the app at launch
```

From `apps/web/`:

```bash
npx convex dev --once           # One-time deploy Convex functions to dev deployment
npx vitest run tests/convex/messages.test.ts   # One test file
```

From `apps/ios/`:

```bash
swift test                      # Japanese text code (casualizer, romaji) as a Swift package, on macOS
```

## Testing

- **Convex tests** live in `apps/web/tests/convex/`, one file per area. They run the real schema and functions against an in-memory backend (`newBackend()` in `setup.ts`), including HTTP routes (`t.fetch`) and scheduled functions (fake timers). Node 22 is needed. `tests/no-network.ts` makes any real network call fail; a test that needs a model's answer stubs `fetch`
- **Web tests** live in `apps/web/tests/web/` and run in the same `npm test`: the readers in `lib/game-teams.ts`, the rule in `lib/game-results.ts` for which Emoji Match game the room page shows, the rule in `lib/textures.ts` for the background outside a room, the rules in `components/ui/logo.tsx` for how long each letter of the room header's wordmark waits before it hops and for which letter a tap is on, and the team screens of Lost in Translation and that wordmark rendered to static markup with `react-dom/server` (no DOM, so nothing is clicked and no effect runs). `textures.test.ts` also holds the texture list, the texture a room is drawn with, and the iPhone app's list and tiles (read as files from `apps/ios`) against each other, and the body of the iPhone app's own pick (`RoomTexture.randomIndex`, which no Swift test compiles) as its file writes it. `room-live.test.tsx` mounts the whole room page with `react-dom/client` in a stand-in browser (`tests/web/dom.ts`: a document React can draw in and a test can read and tap, with nothing laid out or loaded), in vitest's node environment: effects run, a query's answer can change, and the clock is the test's. It holds that the message list and each bubble are drawn again for every change they show and for no other, which rests on the page handing them the objects it handed them before (`lib/stable.ts`, whose own rules are in `stable.test.ts`). It also holds where a room's reactions are read from, in a room with `reactionsByRoom` and in one without, on either deployment, and that both show the same pills at the same moments; and what the page writes for the drawing sheet of Truth or Dare (`participants.setTypingAction`: once when the sheet opens and once when it closes, however often the page is drawn, and once more each time the room shows the action gone under the open sheet); and the vibe meter in the header by the page's own clock (`hooks/use-vibe.ts`: the numbers at each 5-second move, and that a move draws the page only when it changes one), and the results of a Word Rush game the page did not see played going three minutes after the game ended in a room where nothing draws the page. It also holds the things to say over the message box (`components/suggestion-strip.tsx`): what the strip offers as the room talks, falls silent, plays and welcomes, in which language, the display settings that turn it to her own language or off, and that its clock draws the strip alone; and what a tap on one does to the message box (`MessageInputHandle.fill` in `components/message-input.tsx`): the text replaced and nothing sent, the typing notice, a dictation of words ended, the strip out of sight over words of her own and while a voice message records, the field's focus on a computer and a phone's keyboard left as it is, and that a tap draws neither the list nor a bubble. For these the stand-in browser says what the device is pointed at with (`browser.pointer.coarse`, read through `matchMedia`), and the tests give it a speech recogniser and a recorder of their own. `conversation-starters.test.ts` holds the rules that pick those things to say (`lib/conversation-starters.ts`) and the deck itself: every phrase in English, Japanese and romaji as the app writes it. `reactions.test.ts` holds the map the list finds a bubble's reactions in (`lib/reactions.ts`), the hook that keeps that map from one answer of the server to the next (mounted by itself in the stand-in browser), and the two parts that draw them (the pills under a bubble, the row in its sheet), rendered to static markup. `vitest.config.mts` gives them the `@/` alias and JSX; `tests/tsconfig.json` type-checks them, a `.test.tsx` included, along with the components they render
- **Pins** hold what a move must not change. `tests/convex/http-routes.test.ts`: the whole list of HTTP routes (method and path) against `convex/http.ts`; a route added, renamed or removed on purpose changes its line there in the same change. `tests/convex/poll-cost.test.ts`: ceilings on what one poll by the iOS host returns and on what its costly queries read; a change that makes a poll cheaper lowers the ceilings it earned in the same commit. `tests/web/room-page.test.tsx`: the whole guest room page rendered to static markup in each state a first render can show, with `convex/react` and `next/navigation` mocked, and for each state a snapshot of its markup, the queries it subscribed to with their arguments and the mutations it asked for. It also draws by themselves the view components a first render does not reach (`components/room`: the settings sheet, the leave dialog, the join cut-in, the Resume buttons and others), holds the order of the layers that share a z-index, and calls the End Game button's rule (`lib/end-game.ts`). When a change to the page is meant, rewrite the snapshot with `npx vitest run tests/web/room-page.test.tsx -u` from `apps/web` and read its diff. No effect runs there, so handlers, effects and anything behind a tap are not covered
- **Checks for a move** live in `scripts/step6/`, each run with `node` from the repo root and described in its header: `list-routes.mjs` (the HTTP routes the Convex router registers), `line-account.mjs` (every line of a split file accounted for once, apart from an allow-list), `web-move-check.mjs` (a range table: each moved block unbroken and in order, the lines that stay in order) and `hook-order.mjs` (a component's hooks in the order they run, custom hooks opened, compared with a base commit). `scripts/step6/ios/` holds the Python tools that write the files of the iPhone room screen and of its view model from the one file each is at `1b68a6f`, with verifiers; its README gives the procedure. A file edited after the tools wrote it no longer equals their output, and `tree_state.py` then names the state `unknown`. `node scripts/step6/selftest/run-all.mjs` and `python3 scripts/step6/ios/selftest/run.py <new empty folder>` check the tools themselves
- **A test marked `test.fails` with a `DEFECT:` comment** states the correct behaviour for a known bug and passes only while the bug exists. Fixing the bug makes it report "Expect test to fail": remove `.fails` in the same change. `grep -rn "DEFECT:" apps/web/tests apps/ios/Tests` lists every known bug
- **What the in-memory backend does not model:** stored files have no content type (tests set it by hand), there is no concurrency or write conflict, and crons do not run (tests call the cron functions directly)
- **iOS text tests** live in `apps/ios/Tests/`. `apps/ios/Package.swift` compiles a few Foundation-only files from `Services/Processing` in place; it is not how the app is built. A known bug there is an `XCTExpectDefect` line
- **CI** (`.github/workflows/`): `ci.yml` runs type-check, lint, tests, the Convex backup-copy check, the localization check and the web build on every push to `main` or `redesign` and on pull requests; `ios-text.yml` runs `swift test` when the text code changes. `deploy.sh` deploys from the local tree before it pushes, so CI does not gate a deploy; the script runs `npm test` itself before it pushes anything
- **Adding a Swift file under `apps/ios`:** the file is listed in `Enchatto.xcodeproj/project.pbxproj` by inserting the lines XcodeGen would write for it, with `scripts/step6/ios/conversation-view/pbx_add.py` (its header gives the steps). The project is not regenerated: it holds edits a regeneration would undo. `scripts/step6/ios/pbx_insert_only.py` shows that nothing but insertions changed, and the build shows that the file is compiled. XcodeGen reads `apps/ios/project.yml`, which takes every file under `apps/ios` as app source unless `excludes` names it

## Deployment

There are two Convex deployments, and the deployed web app talks to both:

- **Production `basic-ram-104`:** the web app on Vercel (`NEXT_PUBLIC_CONVEX_URL`) and Release (TestFlight / App Store) iOS builds (`AppConfig.swift`)
- **Dev `helpful-bulldog-420`:** local dev (`apps/web/.env.local`), Debug iOS builds, and rooms created by older iOS builds, which the web app reaches through `NEXT_PUBLIC_CONVEX_LEGACY_URL` (`?b=legacy`)
- **Deploy everything:** `./deploy.sh` from the monorepo root, on a committed tree. It type-checks, runs the tests (`npm test`), pushes Convex functions to dev (`npx convex dev --once`), then to production (`npx convex deploy`, which asks before it pushes), then runs `git push`, deploys the web app with `npx vercel --prod --force`, and checks that https://enchatto.vercel.app/api/version reports the new SHA. It needs a terminal for the production prompt, so an agent asks the user to run it rather than running it
- **Order matters:** Convex functions go to both deployments before the web build that calls them. Open tabs reload onto a new web build within a minute (`DeployRefresh`), so a web build that is ahead of its functions breaks for everyone at once. The web's room page passes `token` to `games.getMyActiveStep`, and a server that does not declare that argument refuses the query, which takes the room page down: one more reason functions go first. Keep function changes backward compatible: installed iOS builds do not update with a deploy. An iPhone build can be ahead of its functions too: one with a longer texture list than its deployment counts has its new textures turned down (see Backgrounds), and a Debug build run from Xcode talks to dev
- **Undoing a release:** the schema holds fields that function code from before them does not know: `gameSteps.outputDrawingStorageId`, `reactions.roomId` (with the index `reactions.by_roomId`) and `rooms.reactionsByRoom`. Convex refuses a push when a stored row has a field the pushed schema does not declare, so an older commit cannot be pushed to either deployment once rows carry them. A bad release is undone by a new commit that keeps those fields and indexes, and a bad web build by promoting the previous deployment in Vercel. That commit also keeps what the stored rows rely on: `outputDrawingStorageId` left out of every step a client is sent (`forClient` in `games.ts`: a client that holds a file's id can get the file deleted), the purge deleting that file with its draw step, and `reactions.addReaction` writing `roomId`. A room with `reactionsByRoom` shows only the reactions that have a `roomId`, so if a commit ever stops that write, `reactions.fillReactionRoomIds` is run before summaries are read by `by_roomId` again
- **Vercel:** project `web`, Root Directory `apps/web`, so the CLI must run from the monorepo root. The production branch is `main`; a push to any other branch only creates a preview build. A push to `main` is a production web deploy of `main`'s tree, so only push `main` when it is the commit `deploy.sh` just shipped
- **Convex environment variables** (`ANTHROPIC_API_KEY`, `GROQ_API_KEY`, `APNS_KEY`, `APNS_KEY_ID`, `APNS_TEAM_ID`) are set per deployment. Add a new one to both, from `apps/web/`: `npx convex env set NAME value`, then again with `--prod`
- **Switches, also Convex environment variables, all off when unset:**
  - `AUTH_MODE`: unset or `log` writes an `auth:` warning to the Convex log for a call with a missing or wrong caller token and lets it through; `enforce` refuses it. Set `enforce` only once the log shows no `auth:` lines from current clients
  - `PURGE_CLOSED_ROOMS_AFTER_DAYS`: a number of at least 1 makes the daily `rooms.purgeClosedRooms` cron delete rooms closed for longer than that, with their messages, game rows and stored files. Unset, nothing is deleted. Take a snapshot export before first setting it on production
  - `EMOJI_MATCH_HIDE_CARDS`: `on` makes the Emoji Match queries send face-down cards without their emoji and pair, so the board cannot be read ahead. Unset, the stored board is sent. Set it once iOS builds up to 2a14426 are no longer in use: they turn the host's tapped card over before the server answers and would draw an empty face
  - `LOST_IN_TRANSLATION_HIDE_ANSWER`: `on` makes `games.getMyActiveStep` send a Lost in Translation step only to its own player, and never say which option is right; the answer comes in the reply to the guess. Unset, a step goes to anyone who asks for it, with `correctOption`. The reply to a guess (`games.submitGameStep`, `/api/games/submit-step`) carries the result in both modes, to a caller with the player's token, whatever `AUTH_MODE` says. A player with no token on record is answered once, when the guess is taken; a guess that `AUTH_MODE` lets through without the player's token is taken and answered with nothing (`{"ok":true}` on the route). Set it once iOS builds up to e2c060f are no longer in use (they read `correctOption` off the step and stamp every pick "Wrong!", though the guess is scored correctly) and the web build that reads the reply has been live for a few minutes. Set it on production only, and not on the dev deployment while older Release builds still create rooms there
  - `WORD_RUSH_GENERATIONS_PER_HOUR_MAX`: optional ceiling on Word Rush card generations across all rooms
- **iOS:** Rebuild in Xcode after deploy to pick up new git SHA. The "Inject Git Commit SHA" build phase (in `apps/ios/project.yml` and in `project.pbxproj`) writes the first seven characters of `HEAD` into the built app's Info.plist as `GitCommitSHA` on every build, and `GitInfo.commitSHA` reads it for the label on the start screen and in the room's settings. The phase names the built Info.plist as its input file, which is what makes Xcode run it after writing that file; without it a rebuild writes the Info.plist over the stamp

## Data Flow

1. Participant sends message via web → Convex mutation inserts with `status: "pending"`
2. iOS host polls for pending messages via HTTP actions (1.5s interval)
3. Host processes locally: translation → romaji + suggestions (concurrent)
4. Host submits processed result via HTTP → Convex updates message to `status: "processed"`
5. Web subscribers see the update in real time via Convex `useQuery`

Two translators race on every text message, and whichever finishes first is what people see:

- **The backend** (`messages.translateMessageServerSide`, scheduled by each send) calls Claude Haiku for the translation and for the romaji. Its romaji instruction spells out the iOS app's conventions (particles as spoken, no macrons, lowercase), so a message reads the same whichever side wrote it
- **The host's phone** translates what `/api/messages/pending` hands it, then casualizes Japanese (`MeCabCasualizer`) and writes romaji (`MeCabRomajiService`). The casualizer only shows when the phone wins the race
- A result never replaces an existing translation. If the backend's own attempt fails (no key, an API error), the message waits `HOST_TURN_MS` for a host who is present; after that it is marked failed with `awaitingHost`, stays in the host's queue, and the host's translation replaces the failure whenever it arrives

## Key Patterns

- **Web routing:** `/` (QR scanner + join code) → `/join/[joinCode]` (nickname/avatar/language) → `/room/[roomId]?pid=participantId&tk=1`. `tk=1` marks a link made for a browser that holds the participant's token; opened anywhere else, the room page sends the guest back to the join page
- **Convex React provider:** `lib/convex.tsx` wraps the app with `ConvexProvider`
- **i18n:** Simple `t(key, lang)` function in `lib/i18n.ts` with hardcoded English/Japanese translations
- **iOS ↔ Convex:** `ConvexHTTPClient` POSTs to HTTP action routes. `convex/http.ts` holds the router and nothing else: each area registers its own routes from its own file (`httpRooms.ts`, `httpMessages.ts`, one `http<Game>.ts` per game), and the helpers they share are in `httpShared.ts`. `/api/rooms/snapshot` (`httpRooms.ts`) answers in one request what a host's refresh without it asks for in ten or eleven, all but the replay: each section is the result of the query its own route runs (null where that route says `{"ok":true}`), and a section whose query was refused is left out and named in `errors`. A refusal of the room, its participants or its messages fails the request with 400 instead, as on their own routes, and a failure `jsonAction` answers 503 for (`isTransient` in `httpShared.ts`: a write conflict, an overloaded backend, a refused rate limit) fails the whole request with 503 in whichever section. The host app's refresh (`HostRoomViewModel+Sync.swift`) asks it once and assigns the whole answer in one turn, each game under the rule its own poll has: the room, its participants, its messages and their reactions are all or nothing (without any one of them the refresh fails and nothing is assigned), while a game section that is left out keeps its value. A game whose own fast poll runs is not shown from the snapshot, whose answer is the older one: its section is left out of the request, except Truth or Dare's, which is then read only for a finished answer to have translated. A 404, and only a 404, means a server without the route: the view model remembers it for that visit to the room and makes the ten or eleven requests instead, as a build from before the route does (a Debug build started with `-enchatto_noSnapshotRoute YES` asks a path that has no route, to try this by hand)
- **iOS room screen:** `apps/ios/Views/HostConversationView.swift` holds the struct's state, `init`, `shownTextureIndex`, `body` and the offline translator's bridge (`offlineTranslatorBridge`). Its other members are extensions in `Views/Conversation/` (`HostConversationView+Header`, `+MessageList`, `+Input`, `+Presentations`, `+Games`, `+Sheets`, `+Party`), beside the room's smaller views (the typing bubble, the vibe meter, party mode's layers in `PartyMode.swift`, the QR panel and others). `inputView` (`+Presentations`) puts the handlers, sheets and covers on the input bar through four helpers, applied in the order of its lines. The view model is `ViewModels/HostRoomViewModel.swift`, the class with its state and `init`, and twelve extensions: `HostRoomViewModel+Sync`, `+Messages`, `+MessagePipeline`, `+SendQueue`, `+Room`, `+ReplyIdeas`, and one per game (`+LostInTranslation`, `+WordRush`, `+EmojiMatch`, `+EmojiBingo`, `+TruthOrDare`, `+Dash`). An extension cannot hold a stored property, so state is declared in the main file, and a member that another file names is not `private`
- **Reactions on the web:** the room page reads `reactionsByRoom` off the room it shows. With it, one subscription (`reactions.getRoomReactionSummaries`, in `app/room/[roomId]/page.tsx`) answers for every message: `lib/reactions.ts` makes a map of the answer by message id, the message list hands each bubble its entry, and an entry stays the object it was until that message's reactions change, so a reaction draws the one bubble it is on. A reaction given or taken back makes the server read all of the room's reactions again and send every guest the whole answer (a Convex query update carries the query's whole value), so what one tap costs grows with the number of reactions in the room, where a bubble's own subscription is sent its one message's. Without it (a room from before reactions carried their room) each bubble subscribes to `reactions.getReactionSummary` for its own message, as the sheet behind its heart does while open: the room's query reads every message of such a room, and again whenever one changes. The bubbles subscribe for themselves as well once the server has refused the room's query, which reads every reaction of the room and is refused when that is more than the 32,000 documents one function may read: convex/react throws a refused query where it is asked, `ReactionsFallback` (`components/room/reactions-fallback.tsx`) catches it, and the list is drawn without the one subscription for the rest of the visit, so the conversation stays on screen. The pills under a bubble and the row in its sheet are each a part that draws (`InlineReactionPills`, `ReactionBarPills`) and a part that subscribes and hands it the answer. Neither way shows a reaction before the server has answered for it: the mutations have no optimistic update
- **Games:** Lost in Translation, Emoji Match, Emoji Bingo, Word Rush, Truth or Dare and Chatto Dash, each with its own Convex module and UI components. From four players Lost in Translation can be played as two teams, which the server deals balanced by language (`games.dealTeams`, `/api/games/deal-teams`; it writes nothing); the host starts the game by passing `teams` to `games.startGame` (`"auto"`, or the split it was shown, kept where it still fits whoever is dealt in). Each round's result for the teams is stored on the round's chain when the round ends, and the points clients are sent are read from there, so they never move while a round is open. A start without `teams` is an individual game, which is what installed builds send
- **Offline room (iPhone only):** a room with no connection, opened from the start screen: one phone passed between two people, each writing or speaking English or Japanese. `Views/OfflineRoomView.swift` is the screen, `ViewModels/OfflineRoomStore.swift` keeps the conversation in a file on the phone, and `Services/Processing/OfflineConversation.swift` holds its rules (tested by `swift test`). Translation is Apple's on-device Translation (iOS 18, both language packs), romaji is MeCab, a translation can be read aloud. It talks to no server and nobody can join it; the Simulator has no on-device translation, so a Debug build there answers with a stand-in sentence
- **Chatto Dash:** a 3D obstacle race, five courses back to back, points for each finish; an original game in the style of the app, each racer the avatar they chose for the chat. One engine for web and iPhone:
  - **The game is `apps/web/lib/dash/`.** `sim.ts` is the physics: pure arithmetic on plain objects, no three.js, no clock and no randomness of its own. Every obstacle is a function of the seconds since the round's start signal (`types.ts`: a solid's `motion` and `active`, a ball's `pos`, a wind's `pulse`), so each device works the same course out for itself and the server sends none of it. `levels/` holds the five courses, written with `build.ts` (distances down the course as `d`, heights as the top of a thing); `scene.ts` draws a level with three.js (glossy blocks under one sun that casts shadows, a sky dome and clouds, ink outlines on everything but the clouds, each racer their avatar as a picture that faces the camera with 3D gloved hands and shoes); `game.ts` runs a round on one device; `sfx.ts` makes its sounds. three.js is fetched only once a race is on (`next/dynamic` in `components/dash-game.tsx`)
  - **Racers do not touch each other.** A device simulates its own racer and says where it is about five times a second (`dash.pushState`, one row per racer in `dashRacers`, written over); it asks for the others as often (`dash.getRacers`, a one-shot query, not a subscription: a subscription would send every device every racer's every move) and draws them 0.42 s in the past, between two of their reports. Every `pushState` answers the server's clock, which is how the devices agree on where the obstacles are. That is about ten function calls a second for each racer while a round is on
  - **Practice, with no connection** (`components/dash/practice.tsx`): any course alone against the clock, best times kept on the device. On the web it is `/play/dash/practice`. The iPhone app carries a copy of it, built by `npm run build:dash-offline` (`apps/web/offline/`) into `apps/ios/Resources/DashOffline` and served to a web view from the app's own files under the `enchatto-offline` scheme (`apps/ios/Views/DashPracticeView.swift`, opened from the start screen), so it plays in airplane mode. The copy is committed and nothing rebuilds it by itself: `tests/web/dash-offline.test.ts` fails when the game, its styles or an avatar picture has changed since it was built. Run the build and commit its output with the change
  - **The server keeps the tournament and knows nothing of the courses** (`convex/dash.ts`, table `dashGames`): lobby → racing → results → … → completed, or canceled. A round's start signal is `DASH_COUNTDOWN_MS` after it is set up; it ends when everyone whose device is still talking has finished, `DASH_GRACE_MS` after the first finish, or at `DASH_ROUND_LIMIT_MS`. A finish is timed by the server's clock. Those who did not finish are placed by how far they got and get no points. The result goes into the chat as an `emoji_match_summary:` with `gameType` "Chatto Dash", which a build from before the game draws as a game it does not know by name; no `game:` start line is written, because such a build would name it Lost in Translation
  - **`tests/web/dash-levels.test.ts` holds that every course can be finished:** a stored run of each (the inputs a planning bot held, `tests/web/dash-bot.ts`, in `tests/web/dash-runs/`) is played back through `sim.ts` and has to reach the finish in time. After a change to a level or to the physics, `DASH_BOT=1 npx vitest run tests/web/dash-levels.test.ts` from `apps/web` has the bot play them all again and writes the new runs; a course the bot cannot finish fails there. `/play/dash/lab` is any course by yourself, with no room and no server (`?level=2&cp=1`)
  - **The iPhone app shows the web's page in a web view** (`Views/DashGameView.swift`, page `apps/web/app/play/dash`): native picker tile, cover and Resume chip; lobby, race, results and podium are the page's. The app puts the player's token where the web keeps one before the page loads, tells it the notch's and home bar's size (`--dash-top`, `--dash-bottom`), answers its `confirm()` with an alert, and takes it down when it says `close` or `ended`. The app learns of a game from the snapshot's `dash` section alone (a one-by-one refresh does not ask: a server without the snapshot has no such game) and opens a lobby with `/api/dash/create-lobby`. **The web build is live before an iPhone build that has the game**: against a web app without the page the cover says the race could not be loaded. A Debug build started with `-enchatto_webBase http://localhost:3100` shows the page from a web app running on the Mac
- **Caller tokens, no accounts:** room access is by join code. A client makes a random token when it joins (`participants.joinRoom {token}`) or creates a room (`rooms.createRoom {hostToken}`); the server keeps it in `participantSecrets` and never returns it. Every mutation that acts for a participant takes an optional `token` (`callerToken` on `participants.setHostPushToken`, where `token` is the APNs device token) and checks it with `requireCaller` / `requireMember` / `requireHost` in `participants.ts`; what a failed check does depends on `AUTH_MODE`. The one exception is Emojifyr (the `*Emojifyr*` functions in `games.ts` and the `/api/emojifyr/*` routes): no current build offers it, and it takes no token and makes no check in either mode, so that installed iOS builds keep working. In HTTP bodies the token is `callerToken` (`hostToken` on `/api/rooms/create`, which registers it) and the caller is `callerId`, never `token` (on `/api/rooms/push-token` that is the APNs device token). The web wraps mutations in `useAuthedMutation` (`lib/convex.tsx`); iOS adds both fields in `ConvexHTTPClient`. Participants from before tokens have none and are accepted in both modes. Queries are not gated, except that with `LOST_IN_TRANSLATION_HIDE_ANSWER` on `games.getMyActiveStep` answers only a caller who proves to be that participant (`token` in its arguments, `callerToken` on the route; a participant with no token on record has nothing to prove)
- **Backgrounds:** a room has one of 52 textures, `rooms.background`, an index into `TEXTURES` (`apps/web/lib/textures.ts`) and `RoomTexture.all` (iOS), which list them in the same order. The host app names it when it creates the room (`background` on `rooms.createRoom` and `/api/rooms/create`): the one on its start screen, so the room looks like the screen it is entered from. Without a valid one, or with a retired one, the server makes its own pick: at random among the first ten that are not retired, and never the last room's. The start screen shows the texture of the room there is to rejoin, and a random one when there is none; a web screen outside a room shows the texture of the last room the tab showed (`sessionStorage`), and a random one when there is none. No random pick lands on a retired texture. While a room is open its host can give it another texture (`rooms.setRoomBackground`, `/api/rooms/background`; host only, and an index that is not a texture is refused), and guests' pages follow by themselves, because they draw the index stored on the room. On iPhone a full-screen cover shown from a room (the game task cover, the replay, the drawing composer) draws the room's texture too: the room screen puts its index in the `roomTextureIndex` environment value, which `ecPaperBackground()` reads, and each sheet or cover is handed it where it is presented
  - **The first ten are the ones every build has**, and two rules stay among them however long the list grows. The server's own pick (`PICKED_BACKGROUND_COUNT` in `rooms.ts`, less the retired ones): the app that sends no background is an iPhone build from before the start screen named one, and it ships the tiles of those ten only. And the fallback for a room with no stored index, the FNV-1a hash of its join code modulo ten (`textureForRoom` on the web, `RoomTexture.index` on iOS): every build then draws such a room alike, and a room from before the index was stored keeps its texture. A build handed an index it does not know (an older app in a room whose host picked a newer texture) takes the same fallback. The fallback lands on a retired texture like on any other of the ten: an installed build cannot be told to skip one
  - **A texture is retired, never removed.** Five are: `doodles` (index 4), `alphabet` (9), `brush` (24), `pencil` (25) and `candylines` (26). A retired texture keeps its place in both lists, its index and its tile, and a room that has it is drawn with it: no stored row is rewritten. It is marked in three places, which `tests/web/textures.test.ts` holds equal: `retired: true` on its entry in `TEXTURES`, `retired: true` on its entry in `RoomTexture.all`, and its index in `RETIRED_BACKGROUNDS` in `convex/rooms.ts` (both copies). On the server `createRoom` takes a retired background as one that is not a texture, and `setRoomBackground` does not refuse it: the room gets the server's pick, never the index stored on it, and the answer names it (a room with no stored index has none to avoid, so its pick can be the texture its join code draws it with). An installed build still offers the retired ones (its Random button picks among its whole list); it draws its own pick and takes the room's real background at its next refresh. On iPhone `RoomTexture.randomIndex` leaves them out: the start screen's pick, the Random button, the mock API. On the web the texture of a screen outside a room (`ambientTextureIndex`) is never a retired one: its random pick leaves them out, and a last room that has one counts as none
  - **Adding a texture** takes four things, all in the same order: an entry at the end of `TEXTURES`, the same key and blob pair at the end of `RoomTexture.all`, its tile as a PNG at three times the svg's size in `apps/ios/Assets.xcassets/Textures/tex-<key>.imageset`, and `BACKGROUND_COUNT` in `convex/rooms.ts` (both copies). The tile is the texture's svg on a clear ground, so that the paper shows through it: `rsvg-convert -z 3` of the svg draws it so. The pixels are what makes it the tile: the committed files hold an `sRGB` chunk where the tool writes a white `bKGD` one, so a fresh render is the same picture and not the same file, and the asset catalog compiles the two alike. The asset catalog takes a new imageset as it is, and the Xcode project does not change. Never move or remove one: rooms store the index. `tests/web/textures.test.ts` holds the two lists, the tiles and the server's count against each other. The count is also written out in four places: in that file, which has the list of keys too, in `tests/convex/rooms-participants.test.ts` (`COUNT`), at the top of `RoomTexture.swift` and at the top of this entry
  - **The count is live before the longer list is.** `BACKGROUND_COUNT` is on both deployments before a build that has the longer list is run against them: `./deploy.sh` first, then the iPhone build, a Debug build from Xcode too (it talks to dev). A server that counts fewer takes a new texture's index for no texture. A room made from a start screen that shows one gets the server's pick, so the room is not on the texture of the screen it was entered from. And the Random button's pick of one is refused: the background the room had comes back, under an alert that reads "Unknown background". Functions first costs nothing, because no build sends an index its own list does not have. The web build is live before such an iPhone build too: a page that does not know a room's index draws the room by its join code, and not as its host sees it
- **Things to say:** a row of chips over a guest's message box, to get shy people talking. Worked out in the browser alone from the messages and the clock (`lib/conversation-starters.ts`), nothing asked of a server: answers to the newest message of someone else's for 30 seconds (reactions, yes/no or open answers to a question, reactions to a picture), welcomes for a newcomer and good-game chips for a minute, then topics for the room, the season's first, and a game offered after 90 seconds. Her introduction leads while she has said nothing in the room. The message she is replying to comes before all of it; a game that is on (`gameOn` from `lib/end-game.ts`, lobbies too, whoever asks) leaves nothing else, and so does her own message, until anybody else's (however many of hers came before it) or the silence after it. A phrase said in the last 12 messages, in either language, is not offered again. Every phrase of the deck is written in English, Japanese and romaji: a chip is in her own language, which a tap puts in the box, and the other language under it is hers to turn on or off in the display sheet (on to begin with for a Japanese reader, off for an English one, who has the romaji under the Japanese). The sheet turns the chips off too (`enchatto_suggestPrefs` in `localStorage`, this browser alone); `settings.suggestionsEnabled` turns them off for the room. A message's `processing.suggestions`, or the replies a phone wrote for it in their place, lead the strip, each followed by one of the deck's (none of which says one of them again), so that a phone has both in sight. They are no longer under its bubble on either side; the host's stub writes none. The strip steps aside while the field holds words she typed or dictated herself, and while a voice message records
  - **The iPhone app has the same strip** (`Views/Conversation/SuggestionStrip.swift`, over the input bar in `HostConversationView+Input.swift`), for its host and its guests, with the web's rules ported to Swift (`Services/Processing/ConversationStarters.swift`). Neither the deck nor the rules are kept equal by hand: `tests/web/conversation-starters.test.ts` writes the deck out as `Services/Processing/ConversationDeck.swift`, and 150 seeded situations with the web's answer to each as `Tests/EnchattoTextTests/StarterCases.jsonl` (vitest file snapshots), which `ConversationStartersTests` holds the port to. After a change to either: `npx vitest run apps/web/tests/web/conversation-starters.test.ts -u`, then `swift test` in `apps/ios`. Its switches are in the display menu (`enchatto_showSuggestions` and `enchatto_suggestUnder`, `@AppStorage`); the chip that offers a game is the host's alone. The fade at the strip's edge shows only while more chips are past it
  - **Replies written on the phone.** On iOS 26 with Apple Intelligence on, Apple's on-device model writes three replies for the newest message someone said, for as long as the strip answers it, and for the message being replied to: no request leaves the phone and nothing is paid for them. `Services/ReplyIdeaWriter.swift` asks the model (FoundationModels, a fresh session for each message, given up after 20 seconds); the instructions, the prompt and the clean-up of its answer (`Services/Processing/ReplyIdeas.swift`) are tested by `swift test`; `HostRoomViewModel+ReplyIdeas.swift` queues the messages, one at a time and the newest two at most. The Japanese is the model's, the English Apple Translation's of it where the language packs are installed (the model's own otherwise), the romaji MeCab's. They lead the strip. The host's phone uploads them for everyone else, since a browser has no model: `messages.setSuggestedReplies` (`POST /api/messages/suggested-replies`; host only, three at most, 300 characters at most each) keeps one row per message in `suggestedReplies`, a table of its own because patching a message would send every subscriber the whole message list again. The web subscribes to `messages.getSuggestedReplies` (the room's five newest rows) and hands them to `startersFor` as `ideas`. A guest's iPhone writes its own and uploads nothing. Without the model (an older iPhone, Apple Intelligence off, the simulator, which says the model is there but has no assets for it) the deck alone is offered. The app runs from iOS 16, so `FoundationModels` and `Translation` must stay weak-linked: after touching either, `otool -l` on the built binary shows `LC_LOAD_WEAK_DYLIB` for both
  - **Functions before the web build.** A deployment without `messages.getSuggestedReplies` fails the room page's subscription to it: the functions go on a deployment before any web build that talks to it, previews included. `./deploy.sh` does so by its order
- **Limits:** `takeRateLimit` in `participants.ts` (table `rateLimits`) throttles sends, pictures, dictation and model calls. A refusal's message contains "rate limit", which the routes answer with 503 (`jsonAction` in `httpShared.ts`, and the drawing route's own mapper in `httpMessages.ts`) so the iOS send queue retries

## Schema

Core tables: `rooms`, `participants`, `messages`, `reactions`, `suggestedReplies`. Game tables: `gameSessions`, `gameChains`, `gameSteps`, `emojifyrRounds`, `emojifyrGuesses`, `emojiMatchGames`, `truthOrDareGames`, `truthOrDareTurns`, `dashGames`, `dashRacers`. Schema defined in `apps/web/convex/schema.ts`. A team game of Lost in Translation is a session with `gameSessions.teams` (and `teamAway`), and keeps each round's result in `gameChains.teamRound`; an individual game has none of the three.
